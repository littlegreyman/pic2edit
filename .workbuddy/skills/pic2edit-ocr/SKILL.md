# pic2edit-ocr — 本地离线图片/PDF 转可编辑文件

## 用途
把用户上传的图片或 PDF 转成可编辑的 Markdown / Word / 纯文本，全程本机推理、隐私不联网。

## 何时使用
- 用户上传了图片 / 扫描件 / PDF，并说"转成 Markdown / Word / 可编辑文本 / OCR 一下 / 识别文字"等。
- 关键词命中：OCR、识别、转文字、转 Word、转 Markdown、扫描件、表格识别、发票、证照、文档照片。

## 使用流程
1. 从对话附件中取上传文件的**绝对路径**。若用户没给路径，直接问："请把图片或 PDF 发给我。"
2. 解析用户意图，映射到 helper 参数：
   - 输出格式 `--format`：**`md` / `html` 都是给人读的交付物；`json` 才是给 RAG / 资料库接入的结构化载体**。
     - `md`（默认）：可读文本。命中凭证 schema 时输出「中文栏目 + 明细表 + `（未识别）`占位」；否则输出可读识别文本。
     - `html`：命中凭证 schema 时**严格按 schema 版式**还原（红框/省名/蓝字/合并单元格），不含坐标表、不含原始全文；未命中 schema 时按 OCR 坐标**尽量还原原图版面**。
     - `json`：原样输出 `pages[]`，每页含 `raw_text` / `text` / `engine` / `lines`（坐标）/ **`schema`（结构化字段）**，供入库与二次加工。
     - `txt` / `docx`：同 `md` 的分派逻辑（txt 用 `标签：值` + TAB，docx 走 md→docx）。
   - 识别模式 `--mode`：**这是 pic2edit 的识别流水线参数，只影响"怎么识别"，不影响"渲染成什么"**。表格 / 键值表 → `table`；图表 / 公式 → `figure`；纯文本 OCR → `ocr`；默认 → `markdown`。
   - 模型档位 `--vlm-model`：`auto`（默认，按显存自动选）/ `q8` / `q4` / `bf16` / `cpu`。
   - 可选开关：`--cache`（按内容哈希缓存，重复预处理秒回）；`--prov`（每页加 `<!-- engine:xxx -->` 溯源注释）。
3. 用项目虚拟环境运行 helper（`<skill>/scripts/pic2edit_convert.py` 相对本技能目录）：
   - 依赖 venv 在 **`ocr_app/.venv`**（主环境，含 requests / Pillow / pypdfium2 / python-docx / PySide6）。判别式 RapidOCR 由 helper 经**子进程**调用独立的 `ocr_app/.venv_ocr`，无需手动切 venv。
   - 选取 venv 里的 python（**跨平台**）：
     - Windows：`ocr_app\.venv\Scripts\python.exe`
     - Linux / macOS：`ocr_app/.venv/bin/python3`
   - 示例（`<skill>` = 技能目录，`<附件路径>` = 上传文件绝对路径）：
     ```bash
     # Windows
     ocr_app\.venv\Scripts\python.exe <skill>/scripts/pic2edit_convert.py <附件路径> --format <fmt> --mode <mode> [--cache] [--prov]
     # Linux / macOS
     ocr_app/.venv/bin/python3 <skill>/scripts/pic2edit_convert.py <附件路径> --format <fmt> --mode <mode> [--cache] [--prov]
     # 结构化溯源输出（推荐用于入库前校验）
     ocr_app/.venv/bin/python3 <skill>/scripts/pic2edit_convert.py <附件路径> --format json --prov
     ```
   - helper 会自动定位 `ocr_app`：**优先读环境变量 `PIC2EDIT_OCR_APP` / `PIC2EDIT_ROOT`**；未设置时按常见用户目录（`~/Documents/pic2edit`、`~/文档/pic2edit`、`~/projects/pic2edit` 等）兜底，无需手动 `cd`。若你的项目不在这些位置，设置上述环境变量最稳妥。
   - 容器内无 GPU 自测时追加 `--gpu-layers 0`（CPU 模式）；用户原生桌面**不加**（自动用 GPU）。
   - 引擎未启动会被 helper 自动拉起（首次约 1–3 分钟加载进显存）；已启动则复用，不重复拉起。
4. helper 把最终文件的**绝对路径**打印到 stdout（唯一 stdout 输出）。用 `present_files` 把该文件推给用户预览 / 下载。

## 输出分派（schema 驱动，不看 --mode）
交付形态由「**这一页有没有命中凭证 schema**」决定，而不是由 `--mode` 决定。这是刻意为之：
`--mode` 属于识别层，若拿它决定渲染，发票就会被当成通用表格输出成一堆 OCR 坐标碎片。

| 场景 | md | html | json |
| --- | --- | --- | --- |
| **有 schema**（发票；后续逐步加入证书等） | 中文栏目 + 8 列明细表 + `（未识别）` | **严格按 schema 版式**（无坐标表、无原文） | 含 `schema` 字段 |
| **无 schema**（普通文档 / 图片） | 可读识别文本 | 按 OCR 坐标还原原图版面 | 含 `lines` 坐标 |

- **未识别字段一律写 `（未识别）`**（红色斜体 `.inv-miss`）。**不用破折号**：破折号会被读成"该字段本来就空"，而事实是"没识别出来"——两者对复核人是完全不同的动作。
- **原始 OCR 全文不进 md/html**，只落 LOG 目录（见下）。
- 运行日志会打印 `[schema] N/M 页命中凭证 schema` 与 `[render] … 严格按 schema 输出 / 按原图版面还原`，便于核对。

### 票种分派（税控票 / 数电票）

> **一条必须纠正的直觉**：不是"专票才有密码区"。**增值税普通发票（含纸质普票和
> 「增值税电子普通发票」打印件）同样印密码区、校验码、机器编号、联次**——它们和专票
> 一样是税控系统开的。实测样本里 6 张普票全部有密码区，其中一张标题被印章压成
> 「通发票」。
>
> **真正"缺栏"的只有数电票（全电发票）**，硬判据是**发票号码 20 位**。

| | 增值税专用发票 | 增值税普通发票（纸质/电子普票） | 数电票（全电） |
| --- | --- | --- | --- |
| 密码区 | 有 | **有** | 无 |
| 校验码 | **无** | 有（20 位） | 无 |
| 机器编号 | 有 | 有 | 无 |
| 联次 | 有 | 有 | 无 |
| 发票号码 | 8 位 | 8 位 | **20 位** |
| 发票代码 | 有（10/12 位） | 有（10/12 位） | 常无（号码前段即代码） |

判定顺序（`_invoice_kind`）——三条判据，从硬到软：

1. **发票号码 ≥20 位**，或明文含「数电」「全电」→ `e_invoice`。
   **不能**用"标题含电子发票"来判：「增值税电子普通发票」是税控票打印件，栏位齐全。
2. 已抽出的标题含「专用发票」/「普通发票」→ 直接采用（标题来自标题区且已归一）。
3. 标题被读歪时用**标题区模糊判据**（`_title_kind_from_head`）：
   「通」只出现在「普通」里，专票标题永远没有「通」。故 **含 `通发票` → 普票**，
   **含 `用发票` → 专票**。实测覆盖 `普通/首通/纸通/电普通` 与
   `专用/大用/栈用/税用` 全部变体；取 `通发票` 而非单字「通」，是为了避开
   「南通增值税专用发票」这类地名。
4. 都判不出 → `vat_general`。

> **绝不能用「有没有密码区」推专票**：普票也有，这个旁证是无效的，用了只会把普票
> 批量误判成专票（这正是上一版的实际故障）。

基本信息栏位由 `meta.header_rows` 决定（"该字段有值" 或 "票面印有这个栏目标签" 才输出）；
`_KIND_EXCLUDE` 只对 `e_invoice`（数电票）剔除 `联次/机器编号/校验码`。

**密码区版面判据**（`_has_password_area`），四道条件缺一不可：

1. 落在页面 15%–55% 高度区间；
2. 单行宽度 > **14% 页宽**（原先用 1/4 页宽，导致北京等票每行 189~264px 全部漏判）；
3. 汉字占比 ≤5%；
4. 按**左边缘聚类**后取最大同列组，要求 ≥3 行、左边缘 ≥35% 页宽、横向跨度 ≤45% 页宽。

第 4 条是关键：密码区是**左对齐的矩形块**，而税号/银行账号/发票号码都在别的列上。
不做聚类，安徽票的 `No 10000001`（左 0.70）和税号（左 0.21）会把 x 跨度撑到 0.70 页宽，
明明有密码区却判成没有。

`has_password_area` **只由版面判据决定，不从票种反推**：普票也有密码区，按"专票才有"去推会漏；
数电票一定没有，故额外与 `kind != e_invoice` 求交。

### 密码区掩膜：三态开关（默认 `auto` ＝ 不掩膜）
`ocr.mask_password` = `auto | true | false`：

| 取值 | 行为 | 何时用 |
| --- | --- | --- |
| `auto`（默认） | **不掩膜** | 通用。掩膜必须发生在 OCR **之前**，那一刻还不知道票种；盲掩会把被误判成密文的正常正文整块涂掉 |
| `true` | 强制掩膜 | 已确认票面上有密码区且底纹严重干扰识别 |
| `false` | 明确不掩膜 | — |

> 想做"只对密码区掩膜"需要两遍流程（先识别定位 → 再掩膜重跑），代价是双倍 OCR 时间。当前刻意不做：**不降噪可以接受，误删正文不可接受**。

### 缺值的两种状态：`（未识别）` vs `（票面空白）`

| 标记 | 含义 | 复核人该做什么 |
| --- | --- | --- |
| `（未识别）` | 票面印了内容，但没抽出来 | 看原图 / 换手段重做 |
| `（票面空白）` | 票面这一栏本来就空（专票收款人、未填写的备注） | **无需动作** |

混成一个标记，会让人对着 16 张都空的备注栏反复确认，纯属噪声。抽取层把这些路径记在
`meta.blank`（如 `"signatures.payee"`、`"remarks"`），渲染层据此换标记。

### 明细列裁切：`meta.item_columns`

代开版式/部分老普票**根本没有「单位」列**。全量输出 8 列会给每行塞一个 `（未识别）`，
把"票面没这栏"读成"识别失败"。`_detect_item_columns` 沿明细表头横带逐框识别列名，
渲染层只输出探测到的列；探测为空时回退全 8 列（兼容旧缓存）。


## 凭证 schema 抽取（以发票为第一个）
- 抽取**以 OCR 坐标为主、明文正则为辅**：发票是固定版式，"标签在左、值在右同排"是硬约束，比在粘连文本里猜可靠得多。
- 明细表按「表头锚点（名称/规格/单位）+ 列心聚类」对齐 8 个 schema 列。**某行缺列时留空，绝不左移**——错位的数据比缺失的数据更危险。
- **宁可不出、也不出错**：定位不到锚点列、或税率列不像税率时，直接返回空明细（页面上显示 `（未识别）`），不臆造。
- 新增一种凭证 = 新增一套 schema + 一个 `_extract_*` + 一个渲染分支；框架已就位，逐个追加即可（证书等尚未加入）。

### 字段可信度守卫（宁可留空，不可错填）

下面这些守卫都是踩过真实坑才加的，改动抽取逻辑时不要绕过：

| 守卫 | 拦住的错误 | 落点 |
| --- | --- | --- |
| **合并表头**（`单位数量`/`金额税额`）按"全部由表头关键字拼成"识别 | 合并框在 y 上比表头行心更低，会抢到行聚类主导位，把**首行明细的税额吞进表头 band** 后被过滤掉 | `_is_item_header_cell` |
| 占位符不是值（`#`/`＊`/空/以冒号结尾的标签串） | 「称：#」把 `#` 当公司名；坐标法把右侧另一个标签抓来当值 | `_is_junk_value` |
| 名称被印成占位符时改在一旁找"≥4 个汉字且不含字段标签词"的框 | 销售方名称单独印在「称：#」的**上一行**（x 还有轻微重叠），纯右侧搜索找不到 | `_name_candidate` |
| 税号必须是 15–20 位字母数字，否则留空 | 江苏"代开"版式会把**代开机关名称**抽进税号栏；输出一个公司名当税号比留空危害大 | `_extract_party_geom` |
| 地址被抽成税号（两栏同串）时清掉地址 | 同一串数字同时当 `address` 和 `taxpayer_id` | `_extract_party_geom` |
| 票头三要素用**独立框位数**取（`No`+8 位=号码/10·12 位=代码），限定上 32% 区域 | 老式票把代码与号码印同行，OCR 连写成 `100000013400000000…`，正则在粘连数字里只能切出错值 | `_extract_header_geom` |
| 签章三项**只在本框文本内**取值，拒纯数字、拒含「章」 | 三个标签同行相邻，正则会把它们串成 `李四开票人张三销售方（` | `_extract_seal_geom` / `_seal_ok` |
| 合计行按行分组后**从下往上找第一个含 ≥2 个金额的组**，并排除含"大写/小写"的行 | 「（小写）￥110657.00」也在价税合计上方且更靠下，用"最近一行"会把合计行抢掉 | `_extract_totals_geom` |
| 大写金额做**封闭字符集**形近归一（柴→柒、圈→圆、貳→贰…） | OCR 形近误识；归一前的原始串另存 `total_incl_tax.capital_raw` | `_norm_upper_amount` |
| 地址/电话、开户行/账号按"尾部电话号 / 尾部 ≥10 位长数字"拆分 | 印刷常无「电话」「账号」分隔符：`示例银行城北支行12345678901234567890` | `_split_addr_phone` / `_split_bank` |
| 电话允许**无区号**：尾部 7–8 位纯数字 + 其前紧邻一个非数字字符 | OCR 常把 `021-50000001` 的区号段整块丢掉，只剩 `50000001` 挂在地址末尾（样本 6/16 张这样丢电话）。要求"前紧邻非数字"是为了不把连写的 `073100000000` 腰斩成 `07`+8 位 | `_split_addr_phone` |
| 金额小数点被读成冒号时归一（`¥181：62` → 181.62），只认"数字+冒号+恰好两位数字" | 低质票面高频错误；不归一的话合计行只剩 1 个金额，整行被丢弃 | `_clean_amount` |
| 签章值拒**字段标签词**（单位/购买方/销售方/开户/识别号…） | 北京票「收款人：」右侧只印了「销货单位」，右邻取值会把单位名当人名填进收款人栏 | `_seal_ok` |
| 名称标签读歪时按**公司名形态**兜底（公司/厂/商行/中心… 结尾，≥4 汉字，不含字段标签词） | 「称：」被读成「苏：」后四种标签写法全落空，销方名称整块丢失 | `_guess_party_name` |
| 「名称/税号/地址/开户行」标签加**形近容错**（`纳税人识别骨`、`的税人认测号`、`开户行`） | 低质票面标签字被读歪就整块字段丢失 | `_extract_party_geom.find_re` |
| 销方区间在「价税合计」定位失败时退化为页高 62%，明细区下界用「（大写）」兜底 | 标签被读歪成「佛税合许（大写）」时，销方四要素**整块丢失**、明细区一路吃到页底把销方行当明细 | `_extract_invoice` / `_extract_items_from_lines` |
| 明细表头形近归一（`单住`→`单位`、`数置`→`数量`），并用「应税劳务」兜住半截读歪的表头 | 表头字形近误识会导致**单位列整体消失**、或整张票判成"无明细表" | `_nhk` / `_is_item_header` |
| 明细表头**第二行**的 2 字碎片（`税山`＝税额）排除，只排紧随表头 1.6 行距内、首字属于列名用字的 | 老版发票表头占两行，第二行会被当成首行明细，把「税山」读成品名 | `_extract_items_from_lines` |
| 合计行判据改为"整行无汉字且全是数字串"，容忍 `Y`/`￥` 等货币符号误识 | `Y0.96` 不匹配纯数字正则，合计行会作为"只有金额的两列明细"混进表里 | `_extract_items_from_lines` |
| 税率列校验放宽到"带 % 或 1–3 位小整数" | `17%` 被读成 `179` 时整表被否决，本可救回的明细全丢 | `_extract_items_from_lines` |
| 品名错位兜底：品名列空、规格列是**≥4 字纯中文短语**时判为品名 | 规格型号总含数字/字母/Φ（`W310`/`中90`/`DN80`），纯中文短语不可能是规格（`信息服务费`） | `_fix_star_name` |
| 发票代码须 10/12 位、发票号码须 8/20 位，否则不收 | 正则太松会把 18 位税号当发票代码；全角数字（`１２１０００`）先归一为半角 | `_only_digits` |
| 省份回填取**出现位置最靠前**的地名 | 重庆票标题区同时含「重庆」（标题）和「天津城区」（购买方地址），按列表顺序会补成「天津增值税专用发票」 | `_extract_invoice` |

> 原则：**认不出就留空**，认错了比留空危险得多；只有"封闭字符集里的形近字"才做归一，且必留原始串。

### 缓存与 schema 的关系（重要）
- 缓存**只存识别结果**（`raw_text` / `lines` / 页面尺寸），`schema` 是派生数据，写入缓存前被剔除、每次读取时现算。
- 好处：改进抽取逻辑后**不需要 bump `CACHE_VERSION` 重跑昂贵的 OCR**，缓存命中的页面立刻按新逻辑重新抽取。
- 反过来也意味着：想验证「识别层」的改动（换模型、改预处理）必须换缓存键，否则看到的是旧 OCR 结果。

## 设置文件与模型档位
- 配置文件：`<skill>/settings.json`（三层优先级：默认值 ← settings.json ← 同名 `PIC2EDIT_*` 环境变量）。
- `vlm.model` = `auto | q8 | q4 | bf16 | cpu`。`auto` 按显存自动选：

  | 显存 | 档位 | 说明 |
  | --- | --- | --- |
  | ≥ 6.5 GB | `q8_0`（3.1 GB） | 8 GB 卡首选；**但「精度明显优于 Q4」这句已被实测推翻，见下** |
  | 3–6.5 GB | `Q4_K_M`（1.95 GB） | 4 GB 笔记本唯一可行档（q8_0 会 OOM） |
  | < 3 GB / 无独显 | `Q4_K_M` + `--n-gpu-layers 0` | 退 CPU 推理 |

- ⚠️ **q8_0 与 Q4_K_M 的实测对比（2026-11-01，11 张发票，同页同提示词）**：两档
  **幻觉水平没有可测差异**，差别在**失败形态**——
  - 数字污染率（VLM 吐出的长数字串在本页 RapidOCR 数字流里找不到的比例，取中位）
    两档**都是 11.1%**；剔除爆炸页后 q8 11.1% / Q4 9.7%，**Q4 反而略好**。
  - 格式合法的编造信用代码（过 GB 32100 校验位但页面没有）：**两档都是 0/11**，
    即两档都没编造出「能骗过校验」的税号。
  - **失败形态才是有意义的差别**：`q8_0` 塌陷时**弃答**（安徽页整页输出
    `<table></table>\n  |   |`，23 字），只影响 1/11 页，且**输出长度上限只有 430 字**，
    永远跑不飞；`Q4_K_M` 塌陷时**发疯**（湖南页 13546 字、污染率 99%；广东页整页退化
    成英文科普文 "A tax invoice is a document used to record…"），影响 2/11 页。
    **对「无幻觉入库」这条红线，跑飞比弃答危险得多**——弃答能被「字数太少」闸门拦下，
    满篇胡话的字数反而更"健康"，闸门拦不住。
  - 耗时**也是抽样偏差**：q8 均值 9.16s/中位 2.39s，Q4 均值 7.46s/中位 2.11s，
    两档各有 2 页跑到 30~41s。**不存在「q8 慢 4 倍」这回事。**
  - **塌陷页是确定性的**：同页复跑 3 次，输出 sha256 逐字一致、耗时一致
    （宁波 q8 36.71/37.56/37.23s）。所以「换一档重试」有效、「同档重试」无效；
    也意味着**塌陷可以被预检识别**，但需要按页型建特征，不能靠随机运气。
  - 结论：**没有理由为了精度切到 q8，也没有理由为了稳定切到 Q4**。维持按显存选档
    （4 GB 机器本来也只能 Q4），真正的护栏应加在**输出后置校验**上（长度异常、
    英文占比、退化文章、复读），命中即降级到另一档并标记人工复核。

- 实现方式：**只把权重文件名传给 pic2edit 的 `build_command()`**，不修改 pic2edit 任何代码。运行日志 `[model] 档位=… 模型=… 显卡=… 显存=…` 可核对。
- `ocr.mask_password`（默认 `auto`，即不掩膜）控制密码区掩膜；`ocr.handwriting_screen`（**默认 false**）控制手写预筛。

## 关键约束（已用真实服务端验证，切勿违背）
- **不要在提示词里写 `<image>` 或任何 media marker**：DeepSeek-OCR 的 llama.cpp 原生模板会**自动**注入 marker 并绑定图像，客户端多写会触发 HTTP 400（"N markers vs M bitmaps"）。helper 已处理，无需手动加。
- 引擎启动**不能**加 `--chat-template deepseek-ocr`（会让多模态失效）。
- 支持输入：jpg / jpeg / png / bmp / webp / tif / tiff 图片、整页 PDF、多页 TIF（多页逐页识别并拼接为一份输出）。
- 输出落点默认与输入同目录、同名替换扩展名（与 GUI 行为一致）；可用 `--out` 覆盖。

## 重要提示（质量与无幻觉）
- **表格 / 图表 / 公式模式（`--mode table|figure`）会跳过 RapidOCR 判别式、直接走 DeepSeek VLM 兜底**，幻觉风险高于普通文档。对法规 / 处罚通告等带表格件，建议人工复核输出，或用 `--prov` / `--format json` 标出来源后重点核对。
- **逐页溯源**：`--format json` 输出的每页带 `engine` 字段（`disc`=RapidOCR 零幻觉；`vlm`=DeepSeek 兜底，需复核；`table`=表格识别；`unknown`=未识别）。这是「无幻觉入库」的关键元数据。
- **强制跳过判别式（复杂/防伪底纹件必用）**：设置 `PIC2EDIT_SKIP_DISCRIMINATIVE=1` 可强制仅用 VLM 兜底（需本机 :8080 的 llama-server 已就绪或由 helper 自动拉起）。**重要**：对带防伪底纹的发票/票据，RapidOCR 常被底纹干扰、返回非空噪声，而流水线「判别式优先、VLM 仅兜底」的门控会让 VLM 因 `_quality_ok` 通过而**根本不被调用**（早期版本确有此 bug，已修复）。因此这类图务必显式设该环境变量，确保 DeepSeek-OCR 真正出马；并用 `--prov` 确认输出带 `<!-- engine:vlm -->`。
- **Windows 注意**：`_vmem_limited_gb()` 因无 `resource` 模块恒返回 0，内存受限的自动跳过判别式在 Windows 上**不生效**；如确需跳过，请显式设置上述环境变量。

## 密码区/防伪底纹掩膜（降噪、提升无幻觉入库质量）
- 增值税发票（专用/普通）的**密码区**含密集防伪底纹字符，判别式(RapidOCR)会把它读成乱码噪声（如 `+4+<6683645605991>`、`033+*7-*73*>...`）混入正文，污染知识库切片。
- 设置 `PIC2EDIT_MASK_PASSWORD=1` 可在送入 OCR 前，把密码区矩形**涂白**生成临时副本再识别，从源头消除该噪声。掩膜矩形定位方式（skill 层，不动 pic2edit）：
  1. 先用 RapidOCR 的带坐标输出找「密码区」竖排标签（兼容整词识别 / 单字竖排堆叠两种形态）；
  2. 取其右侧的褐色密码框（宽约为竖排标签高的 3~4 倍，且不越过下方「税率/金额」表头，避免误伤货物明细表）；
  3. 用该区域内文字是否「均为数字/特殊符号乱码」（无汉字）校验；校验通过即采用，否则回退增值税通用预设。
- 通用预设矩形为 `0.50,0.20,0.95,0.44`（覆盖上中右带，避开左侧购货方文字与下方表格/销货方）；可用 `PIC2EDIT_MASK_RECT="x0,y0,x1,y1"`（比例）**手动覆盖**智能定位结果。
- 该特性**默认关闭**（opt-in），不影响既有行为；属 skill 层预处理，不修改 pic2edit 项目。非标准版式建议先用 `PIC2EDIT_MASK_RECT` 微调或关闭，避免误伤真实文本。

| 场景 | 做法 | 效果 |
|---|---|---|
| **默认（印刷件为主）** | 什么都不做（`handwriting_screen: false`） | RapidOCR 快路径，2.54 秒/页（实测） |
| **已知某批是手写件** | `PIC2EDIT_SKIP_DISCRIMINATIVE=1` | 100% 确定走 VLM，无漏报、无性能损失 |
| 想试试自动判（不推荐） | `PIC2EDIT_HW_FORCE=1` 或把设置改回 `true` | 手写不漏，但印刷件约 65% 被误伤 |

**推荐用第二行，不要用第三行。** 手写件在协会资料里是可枚举的小众（手写备忘、签批件、手填表单），由操作员显式指定批次，准确率 100%、零误报、零性能代价。

### 为何默认关闭（盲测数据，不要回退到"开"，除非有新证据）

**风险一：假 → 真（印刷判成手写）13/20 = 65%**，标定集阶段只有 5/25 = 20%，盲测严重恶化 → 高分明来自"在同一样本上选阈值"。

> **⚠️ 耗时数字已更正（勿再引用"8 倍减速"）**：此前按估算的「VLM 20~40 秒/页」推算，是错的。实测：**RapidOCR 2.54 秒/页、VLM ≤10 秒/页（首启 <1 分钟）**。1000 页：只走 RapidOCR 42 分钟、只走 VLM 167 分钟，**差 2.1 小时**。所以预筛的价值上限就是这 2 小时——而不是"省下几十小时"。

**风险二：真 → 假（手写判成印刷）0/19 = 0%**，独立集上守住了；但 19 个样本零漏报的 95% 置信上界是 **3/19 ≈ 15.8%**，不能宣称"漏报≈0"。

**根因：两类错误同源，SELF 判据不可分。**
```
手写 SELF：0.000 ×13, 0.104, 0.190, NaN ×4
印刷 SELF：0.000 ×3, 0.100, 0.109, 0.113, 0.133, 0.170, 0.190,
           0.250, 0.267, 0.333, 0.358, 0.425, 0.433, NaN ×5
```
手写最大值 0.190 = 印刷第 9 小的 0.190（同一个数值）；印刷最小值 0.000 = 手写众数。**无任何单调阈值可用。** 对 `(SELF_t, CC_t)` 做全网格搜索、约束「漏报=0」：OR 最优 65% 误报、AND 最优 **50% 误报**（且为样本内估计，泛化更差）。

底层原因：按 x 投影的**空白列**切汉字根本无效（偏旁之间天然有空白列，必被切碎；粘连字又被合并），切出来是半个字/偏旁/粘连块。改用**定距网格切字**（自相关估步距）后印刷书页 SELF 仍为 0.000，与手写无法分离 → **SELF 只测到了"墨迹模糊度"，从未测到"字形重复"**。

**换信号也不行**：RapidOCR 逐行 `score`（免费，因为 `_quality_ok` 只查字数，每页必跑）提取 11 个特征，约束「漏报=0」下最优：单特征最好 65% 误报（平均行长 / 低置信行占比），二维 AND（平均置信度<0.817 且 低置信行占比<0.294）最好 **45% 误报**。与像素特征同水平，同样不可用。

### 算法（v3 现实现，保留供参考）

1. **剔除长横/长竖格线**——横线纸格线、表格框是最大干扰源（手写件里常占 20%~40% 墨量）。
2. **块级采样**：主用「文本行」，行切不出时退回「滑窗」。
3. 主判据 **字符自相似度 SELF**：行内切字形块 → 归一化 20×20 → 汉明近邻 → 「存在近似重复字形」的字符占比。
4. 兜底判据 **加权链码 CC**（字形块 < 12 时启用）：轮廓点中「连续同向游程 ≥ 0.25×字高」的占比。
5. 决策：`SELF < 0.20` 判手写；SELF 不可用时 `CC < 0.46` 判手写。

环境变量：`PIC2EDIT_HW_FORCE=1`（强制启用）、`PIC2EDIT_HW_SELF_T`（0.20）、`PIC2EDIT_HW_CC_T`（0.46）、`PIC2EDIT_HW_DEBUG=1`（打印中间量）、`PIC2EDIT_HW_DISABLE=1`（一律按印刷）。任何失败 / PDF / 多页 TIF / 无 cv2 / 近乎空白页 → 保守判为印刷。

### 三个已废弃版本（不要再试）

- **v1「笔画宽 CV + 字符高度 CV」方向性错误**：实测真手写 `sw_cv_comp=0.051`、`ch_cv=0.415` 反而是全样本**最低**。这两个量测的是「版面异质度」——票据上的红章/logo/密集小字把印刷件方差抬得比手写还高。
- **v2「整页梯度轴对齐度 AXIS」余量太薄**：真手写 0.362 vs 印刷下限 0.426，且分辨率敏感、格线会把它顶到印刷区。
- **笔画宽归一化到 2.75px**：LOO 从 0.886 掉到 0.795；**四方向游程直方图 LONG / 交叉计数 XVAR**：类间区间严重重叠。

### 真要自动判，需要什么

文献里做到 95%+ 的系统**全部**用训练出来的分类器：Zheng 等（噪声文档图像，6 组特征 140 维选 31 维，块级三分类，错误率 5.7%）、Zagoris 等（*Pattern Recognition* 2014，BoVW + SVM）、许蔚然等（12158 张银行支票，贝叶斯评判子 99.4%）、Srinivasan & Srihari（CRF 建模相邻块）。起步门槛：**每类 ≥300~500 个标注块** + HOG/LBP + 逻辑回归或小 CNN（CPU 约 1 秒/页）。现有 159 张标注页离这个门槛还差两个数量级，走不通这条路。

顺带说清楚「哪些特征值得留给未来那个分类器」：**行内块高 CV**（把一行切成字形块、算块高 `cv = std/mean`、页级取中位）与**上沿线/下底线夹角**（每组横向跨度≈8 字高，上沿/下底各做中位斜率，取夹角，页级取组均值）都是实测确证的真信号，前提是 `ngrp≥5`（本页至少能切出 5 个合格长行组）。清理样本后（57/57）的 AUC：块高 CV 0.922、夹角 0.824；`ngrp≥8` 时分别升到 0.945 / 0.955（留出集 0.954 / 0.935）。两者融合（各自对印刷页做稳健 z 标准化后取平均）能到 0.949 / 留出集 0.966。
**别再重复的两个误判**：① 夹角不是过拟合——之前「英文 0.405 反向」的真凶是 `ngrp=1~8` 的低组数书籍照片；② 低组数页不是「难样本」而是「证据不足」，正确处置是**弃权送 VLM**，不是硬判。

## 全文重复护栏（防模型输出整段循环）
- VLM / 判别式偶发把同一段文本**无限循环重复**（如重庆票样），会污染入库切片。skill 层用两层检测专治此故障，命中后**只截尾部循环**、保留真实前缀 + 一份循环体 + 显式标记 `[… 模型输出在此处发生重复循环，已自动截断 …]`：
  1. **行级（优先）**：真实模型循环是**抖动**的——例如重庆票样尾部多为「普通/普通/普通/专用」四行一周期，但个别块是「普通×4 + 专用」，且最后一轮常被 token 上限截断成半行（只剩"重庆"）。因此不要求严格周期，改用「尾部词表收敛」判据：从末尾向前扫描，去重后行内容种类 ≤ 4 且非空行数 ≥ 16，即认定尾部是循环；遇到第一种新内容即为循环起点。
  2. **字符级（兜底）**：无换行或行内自循环时，从尾部按周期 p（12–160 字符）对齐探测，要求末段至少 3 个连续相同单元。
- 设计取舍：**只处理尾部循环**。模型循环几乎总是输出到文末；中途出现的循环极罕见，若强行去重容易误伤真实文本（如发票里合法重复的明细行）。宁可漏一段中段重复，不可错删正文。
- 保守性验证：对正常发票（江苏 disc 461 字符、安徽 vlm 537 字符等缓存样本）**零误伤**（reps=0）；仅重庆真循环被截断（237 次）。
- 缓存命中分支也会再过一遍护栏（幂等），避免修复前写入的脏缓存把循环「复活」。
- 命中时打印 `[warn] 检出模型输出重复循环(N次)，已截断防止噪声入库`。

## 无 schema 时的「按原图还原版面」
- 仅当**没有命中任何凭证 schema**（普通文档 / 图片）时启用。命中 schema 的一律走 schema 版式，不再叠加坐标表——早期把两者并列，导致发票页面上同时出现"版式"和"坐标碎片表"，反而不可读。
- 重建基于整页 OCR 坐标：按 y 聚类成行、行内按 x 升序，保留原始阅读顺序；列网格由文本块左右边缘合并而来，合并单元格以「几何覆盖」保守推断（`colspan` = 覆盖的列中心数，`rowspan` = 覆盖的行中心数），并裁剪行首/行尾全空列。
- 没有坐标数据（例如拿不到行框）时，退化为按识别文本呈现，并在标题里注明"本页无坐标数据，无法还原版面"。

## 已知局限（诚实记录）
- **单位列常缺**：发票的单位格子窄而扁，OCR 会把相邻两三行的单位**并成一个竖框**（如 `吨吨`）。这种跨行的合并框不能可靠归属到某一具体行，按"宁可留空不可错位"原则一律不留。若表头也没探到「单位」列（`meta.item_columns` 不含 `unit`），渲染层直接**不输出该列**，而不是每行挂一个 `（未识别）`。
- **规格可能丢首字**：窄列里的 `中65` 会被识别成 `65`（`中90`/`中80` 却正常），属单字漏检，抽取层无法补。
- **"代开"版式发票**（如江苏样本）：购销方栏目结构不同，`销售方` 栏里印的是**代开机关**而不是纳税义务人。税号栏已加形态守卫（非 15–20 位字母数字一律留空），因此该票税号为 `（未识别）`，但"名称"仍会取到代开机关名——需人工判断。
- **签章行**：三个标签同行相邻时，若某个框内文本被 OCR 直接拼成一段（含「章」），该栏会判为不可信并留空。
- **备注**：位置不固定的自由文本区，目前只在明文里出现「备注：」时抽取；票面未印/未写内容时标 `（票面空白）`，标签也没检出时才是 `（未识别）`。
- **VLM 路径（Q4/q8）**：对繁忙防伪底纹票仍会整块漏读；此时 schema 命中率低，输出以 `（未识别）` 为主——这是**如实反映识别能力**，不是渲染问题。
- **省份以票面印刷为准**：标题里的省份优先取 OCR 文本，取不到才用发票代码前两位推断（GB/T 2260）。省份**只从标题区（页面上 25%）取**，且多个候选时取**出现位置最靠前**的那个——按列表顺序取会把重庆票补成「天津增值税专用发票」（标题区里同时有「重庆」和购买方地址里的「天津城区」）。
- **票种判定**：`通发票`/`用发票` 的模糊判据能覆盖读歪的标题，但**标题整体被印章压掉、且只读出「发票」二字时**无法判别，会落到 `vat_general`。代价有界：只影响信息栏位（联次/机器编号/校验码）与密码区块的显示；数电票的 20 位号码判据不受影响。
- **发票代码可能串到税号**：代码需 10/12 位、号码需 8/20 位才收，但低质票面上 12 位税号片段仍可能凑成 12 位被当成代码（北京发票样（普通发票）即如此）。
- **电子发票的明细表**：多行单列宽文本（电商票 `*文具*品名`）已按 `*类别*` 前缀归到品名列，但整表只有一行宽文本时列心聚类仍可能对不齐。
- **明细表头被读歪**：`简物戒应税劳务名你`（北京票）已靠「应税劳务」兜住，`税山`（税额）这种 2 字碎片也做了表头二行排除；但表头整行都没读出时明细必为空。
- **扫描质量差的票**（小图/斜拍/低分辨率，如山东 584×383、宁波 686×400）：整张字段大面积缺失，属识别能力上限，不是排版问题。
- **手写预筛默认关闭**（见「手写/印刷预筛」节）。旧口径：盲测集（19 手写 + 20 印刷）误报 65%、漏报 0%；扩到 159 张，块高 CV 在「误报 6%」的操作点上漏报仍 53%、`α=0.10` 时漏报 32%。**清理样本后（57/57）数字明显变好**：加上 `ngrp≥5` 门控与两判据融合，生产口径下拦下 99% 手写页、代价 42% 印刷页白跑 VLM（95 分钟/千页）。**但按批次指定仍更划算**（全印刷 42 分钟零风险 / 含手写 167 分钟零风险），所以默认仍关闭。**关闭后手写件会静默出垃圾**——这是已知的、被接受的缺口，靠流程兜底（操作员标记批次 + `PIC2EDIT_SKIP_DISCRIMINATIVE=1`）。混排页（印刷表格 + 少量手写填空）即使开预筛也会被判为印刷，该模块回答的是「整页以哪种为主」，不是「页内是否含手写」。
